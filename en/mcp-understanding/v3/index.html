MCP can enumerate tools, but it cannot guarantee that the LLM sees or chooses the right one.

02 / DISCOVERY VS SELECTION

The Server knows which tools exist.
Does the model know which one to use?

Tool discovery happens at the protocol layer; exposure at the application layer; selection at the model layer. Confusing them makes failures harder to diagnose.

01MCP enumerates toolstools/list

The Client retrieves tool definitions published by the Server—names, descriptions, schemas, and more.

02Host exposes a subsetallowed / deferred

Depending on configuration, permissions, context, or deferred loading, the Host makes selected capabilities available to the model.

03LLM chooses an actiontool name + args

The model interprets the goal, compares tool descriptions, and proposes a specific call.

03 / THE INTEGRATION LAYERS

We already have APIs and Function Calling.
Why do we still need MCP?

The distinction isn't whether GitHub can be called, but how integrations are standardized, maintained, and reused across AI applications.

PATH A / YOUR APPLICATIONCONCEPTUAL FLOW

OPENAI APIDeveloper interface for model capabilities

Developers can request model reasoning and tool use. How a tool executes depends on the chosen API and application architecture.

FUNCTION CALLINGThe model proposes a function call

In a typical custom function flow, the application executes the function and returns its result to the model. This is not a service-to-service communication protocol.

MCPStandardizing external capabilities

The Client and Server agree on discovery and calling protocols; the Server can still call existing REST or GraphQL APIs.

PRODUCT LAYERApps / Plugins

User-facing integrations. The presence of an external tool does not prove its underlying protocol is MCP.

These paths can be combined: a Host may bridge MCP tools into model-callable functions, or use native integrations. A simple application with two fixed APIs need not adopt MCP.

06 / BEYOND MCP

The tools are connected.
What else does a reliable Personal Agent need?

MCP provides reusable connections, Skills provide task guidance, Workflows constrain steps and state, while persistence and triggers let an Agent resume work across execution cycles.

SYSTEM COMPOSITION
1 / 6LAYERS

Only the connection layer

Tools are available, but cross-tool completion criteria and recovery paths have not been defined.

MCP / API
A Skill ≠ an MCP Server, nor is it a universal workflow engine.

Skills can guide when to call tools and how to handle partial results, but hard constraints, durable state, authentication, and final verification still require the runtime and business systems. A Personal Agent does not require MCP.

This capability puzzle is conceptual; toggling options does not create a real Agent. The Tasks lifecycle extension only works with compatible Clients and Servers and does not replace cross-system transactions or business verification.

07 / TAKEAWAY & REFERENCES

Connect → Decide → Verify.
Three actions. One engineering principle.

MCP standardizes tool connectivity, LLMs make tool selection more flexible, and Agent Engineering makes execution manageable, pausable, and verifiable.

CONNECT

Connectivity is not intelligence

The protocol standardizes discovery and calls; it does not interpret goals for the model.

DECIDE

Reasoning is not execution

The model proposes actions, the Host/Agent manages the flow, and external services perform operations.

VERIFY

A tool call is not completion

Judge the outcome using authoritative business state and external evidence—not a claim that the work is “done.”
